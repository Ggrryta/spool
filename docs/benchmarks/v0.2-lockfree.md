# v0.2 无锁化实验报告：一次诚实的负结果

> 日期：2026-09-14 | 环境：Windows 11 / amd64 / Intel Core Ultra 5 225H / Go 1.24
> 结论：**"无锁 MPSC 优于 mutex"假设在本工作负载下证伪**；
> 但实验意外证明 unbounded.Chan（mutex）具备全场最佳的生产者扩展性。
> 本文档遵循 roadmap §3 原则：性能声称只出现在测量旁边。

## 实验设计

实现 Michael-Scott 式无锁 MPSC 链表队列（`mpsc` 包）：

- 入队：链接式协议（CAS `tail.next` 链接 → 尽力推进 `tail`），
  多生产者单 CAS 竞争点，全局 FIFO；
- 出队：单消费者独占 head，无同步开销；
- Go 特性论证：精确 GC 将活跃局部变量视为根 → 被引用节点地址不会
  复用 → 无需 ABA 防护（无 GC 语言需 tagged/hazard pointer）；
- 唤醒协议：sig 容量 1 + "链接先于信号、排空先于睡眠"时序约束，
  穷举可证不丢唤醒（含 Close 必须发信号的边界——由基准测试抓出的
  真实死锁，已加回归测试）。

## 结果一：无锁在任何生产者规模下都没有反超

泵版端到端 MPSC 吞吐（ns/op，越低越好）：

| 生产者 | mpsc.Chan（无锁） | unbounded.Chan（mutex） | 原生 chan(1024) |
|---:|---:|---:|---:|
| 4 | 160 | 95 | 77 |
| 8 | 208 | 96 | 100 |
| 16 | 213 | **93** | 118 |
| 32 | 226 | **91** | 141 |

"无锁在高生产者数下反超 mutex"的假设未获支持：无锁版随生产者数
单调恶化（160→226），mutex 版全程平坦。

### 根因分析

1. **瓶颈定位错误**：本管道的瓶颈从来不是生产端锁，而是泵的逐值
   交接（每值跨两次 channel 边界：队列→泵→Out→消费者）。生产端
   去锁无法改善一个泵受限的系统。
2. **单 CAS 竞争点的代价**：N 个生产者在同一条 `tail` 缓存行上
   CAS，每次失败重试都要重新获取远程缓存行（RFO）。Go 的 mutex
   在极短临界区下（一次 slice append）先自旋后休眠，实际比
   CAS 重试循环更便宜。
3. **每值节点分配**：链表版每值一次堆分配（16 B/op），mutex 版
   的 backlog 是均摊扩容（0 allocs/op）。

### 过程中的两个修复（均有回归测试）

- **False sharing**：head/tail/approx 同缓存行使 MPSC 吞吐近乎
  减半（189 vs 162 ns）；缓存行隔离后恢复。教训：原子字段布局
  是无锁结构的第一优先级设计项。
- **Close 死锁**：Close 只置标志不发信号 → 睡眠中的泵永不复查
  Drained → Done 永不关闭。包内测试因残留信号侥幸通过，大规模
  基准立即抓出。教训：唤醒协议的"关闭"边必须与"数据"边同等
  严格地论证。

## 结果二（意外收获）：mutex 版具备全场最佳扩展性

unbounded.Chan 在 4→32 生产者间吞吐完全平坦（91~96 ns），16+
生产者时全场最快（比原生 chan 快 25%~35%），同时提供原生 chan
没有的无界容量与优雅排空关闭。

原生 chan 在 16+ 生产者时因单锁竞争退化（77→141 ns）；我们的
mutex+泵结构中，临界区极短且泵是恒定速率的"限流器"，生产者
在锁上排队但不放大延迟——限流器结构反而获得了扩展性。

## 结果三：结构下限

Out 通道加 64 缓冲的实验：mpsc.Chan 改善 12%（160→141），
unbounded.Chan 无变化（95→94，噪声内）。泵结构每值两次 channel
交接 ≈ 2 × ~45 ns，~90 ns 是该结构的物理下限；对齐原生 chan
（一次交接 ~77 ns）需要消除一跳，即放弃泵/放弃 channel 语义——
与 API 契约冲突。

决策：unbounded.Chan 回退无缓冲（无可测收益，不弱化背压语义）；
mpsc.Chan 保留缓冲（有实测收益）。

## 处置（按 roadmap §9 假设 3 的证伪条款）

1. **mpsc 包保留、标记实验性**：作为纯数据结构（`mpsc.Queue`，
   Peek/Pop API）与协议正确性的文档化样本；不推荐作为性能选项
   （本库自己的基准显示它全面落后）。
2. **mpsc.Chan 不转正**：未通过 §2 准入测试（"单独发布是否有人
   愿意切换"——答案是否）。可能的翻盘路径：分片化设计（v0.2.1
   探索项，需接受跨分片乱序）或等待 pump-free 的 API 形态。
3. **v0.2 DoD 修正**：原目标"MPSC ≤80ns（4 生产者）"未达成
   （94 ns）；达成项改为"16+ 生产者全场最快 + 平坦扩展性"——
   这对事件聚合场景（多 goroutine 汇报）是更有意义的维度。
