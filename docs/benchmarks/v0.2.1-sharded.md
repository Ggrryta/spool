# v0.2.1 分片化实验报告：目标达成

> 日期：2026-09-14 | 环境：Windows 11 / amd64 / Intel Core Ultra 5 225H / Go 1.24
> 结论：**MPSC ≤80 ns 目标达成**——独立 key 下 50.6 ns（4 生产者），
> 全规模 38~51 ns；即使全部生产者挤同一分片的最坏情况（71~77 ns）
> 也低于目标线且快于 unbounded.Chan。

## 设计（Kafka 分区模型）

v0.2 证伪了"单点无锁"，但也定位了真瓶颈：SPSC 泵版 33 ns vs MPSC
94 ns 的差距就是生产端锁竞争。v0.2.1 的解法不是更快的锁，而是
**让竞争消失**：

```
Put(key, v) ──key 路由──▶ 分片[0..N) ──泵批量窃取──▶ Out
                （每分片独立 mutex+slice）  （一次锁一批值）
```

1. **显式 key 分片**（契约变更，调用方必须理解）：
   同 key 严格 FIFO，跨 key 顺序不保证——Kafka 分区式取舍。
   需要全局 FIFO 的场景仍然用 unbounded.Chan。
2. **分片内核用 mutex 而非无锁**（v0.2 的教训）：无竞争 mutex 快路径
   ~15 ns，远比 CAS 失败重试便宜；竞争由分片消除，而非由锁算法消除。
3. **消费端批量窃取**：泵一次加锁取走整个批次，锁成本按批摊销——
   这也解释了为什么"同 key"最坏情况（全生产者挤一个分片）仍然
   快于 unbounded.Chan（76 vs 95 ns）：后者的泵每值一次锁。
4. **精确计数免锁扫描**：每分片 count 在锁内更新，恒等于
   len(backlog)，泵的空扫描与 Drained 判断完全免锁。
5. **唤醒协议复用**：sig 容量 1 + "先改状态后发信号"，含 Close
   必须唤醒的边界（v0.2 死锁的回归测试已覆盖）。

## 结果

| 生产者 | ShardedChan8（独立key） | ShardedChan8（同key） | unbounded.Chan | 原生 chan(1024) |
|---:|---:|---:|---:|---:|
| 4 | **50.6** | 71.0 | 94.3 | 78.9 |
| 8 | **38.4** | 76.8 | 95.8 | 90.4 |
| 16 | **40.1** | 75.9 | 88.4 | 118.4 |
| 32 | **42.7** | 75.9 | 91.0 | 141.5 |

（ns/op，越低越好；unbounded.Chan 与原生 chan 数据取自同日
BenchmarkMPSCScale 运行。）

### 解读

1. **目标达成**：4 生产者 50.6 ns，比 80 ns 目标低 37%；比
   unbounded.Chan 快 46%，比原生 chan 快 36%。
2. **扩展性反而随生产者数改善**（50.6 → 38.4）：生产者并行度
   提高后，泵的批量窃取批次更大，摊销更充分。32 生产者时比
   原生 chan 快 3.3 倍。
3. **同 key 最坏情况也有 20% 优势**（76 vs 95 ns）：单分片的锁
   竞争与 unbounded 相同，赢在消费端批量窃取。即：即便完全不用
   分片路由，只把 unbounded 的泵换成批量窃取也有收益。
4. **0 allocs/op**（B/op ~43 为 backlog 的均摊扩容），分片版没有
   v0.2 无锁版的每值节点分配问题。

## 处置

1. **ShardedChan 通过 §2 准入测试，转正**：对"有天然 key 的多生产者
   汇聚"场景（连接事件、按 ID 的请求聚合），它比所有对比对象都快，
   代价（跨 key 乱序）显式写在 API 上。
2. **mpsc 包内部分级**：ShardedChan（生产可用）> Queue/Chan
   （保留为实验性文档样本）。
3. roadmap 假设 3 以修正形式验证成立："分片化（而非单点无锁）
   可达成 MPSC 性能目标"。

## 待决

- 生产者数远超分片数时（如 128 生产者 / 8 分片）的行为未测，
  下次基准扫描扩展范围。
- 泵的轮询顺序（分片 0 优先）在高压下的公平性未观测；
  如有饿死案例，改为每次扫描起点轮转。
