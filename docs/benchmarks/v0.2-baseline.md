# v0.2 基线基准报告：Unbounded vs 生态在位者

> 日期：2026-09-14 | 运行：单次（正式 CI 对比将使用 `-count=10` + benchstat）
> 环境：Windows 11 / amd64 / Intel Core Ultra 5 225H（14 核）/ Go 1.24
> 代码：`bench/bench_test.go`（独立子模块，主库保持零第三方依赖）

## 结论速览

1. **全面碾压 chanx**：所有场景快 4~15 倍。chanx 的"双通道 + 泵 + 环形缓冲"
   架构每条消息要付 3 次跨 goroutine 交接，成本巨大。
2. **对原生大缓冲 channel 基本打平**（快路径 57 vs 53 ns），而原生 chan
   容量固定、满了会阻塞——我们在"同等性能"下提供了无界容量。
3. **MPSC 是我们的明显短板**（112 vs 原生 75 ns）：单一 mutex 把 4 个生产者
   串行化。**这是 v0.2 无锁化的明确靶子。**
4. 意外发现：自动泵版 `Chan` 在多个场景反而快于手动版 `Unbounded`——
   泵把消费者的 `Load` 从用户 goroutine 移到泵里，与生产者的锁交互
   形成了流水线并行。详见"发现"一节。

## 分析

### 为什么 chanx 慢一个数量级

chanx 的数据通路是 `In channel → 泵 goroutine → 环形缓冲 → 泵 → Out channel`，
每条消息最少 3 次跨 goroutine 交接（各含一次调度与唤醒），而我们的
手动版只有 1 次（`Put` 直递 `Get` 通道），泵版 2 次。无界队列的正确
成本模型就是**交接次数 × 单次交接成本**。

### MPSC 短板是设计使然，也是 v0.2 的靶子

`Unbounded` 的 `Put`/`Load` 共用一把 mutex，4 个生产者 + 消费者的
`Load` 全部在这把锁上排队（112 ns 里锁竞争占大头）。原生 channel 的
发送路径是无锁队列 + 细粒度锁，多生产者扩展性更好。

**Vyukov 式 MPSC 无锁队列**（每生产者独立 slot + 序号协议，写者只写
自己的 slot，无生产端竞争）正是针对这个问题的标准解法，且天然保留
我们已有的能力假设。目标：MPSC 场景对齐原生 chan（≤80 ns），
同时保住"无界 + 排空 Close"语义。

### 发现：泵版反而更快，值得利用

手动版里，消费者的 `Load` 与生产者的 `Put` 在用户 goroutine 上直接
争锁；泵版把 `Load` 移入泵 goroutine，生产者→泵→消费者形成三级
流水线，锁交互被时间上错开。这意味着 v0.2 无锁化之后，两个版本的
分工更清晰：手动版主打"零 goroutine 极致嵌入"，泵版主打吞吐。

## 已知局限

- 单次运行，Windows 计时器粒度与调度噪声未消除；正式结论以
  `-count=10` + benchstat 的统计对比为准（纳入 CI 后补）。
- 堆积场景的 B/op（~40-47）是 backlog slice 的均摊增长，非每条消息
  独立分配（allocs/op = 0）。
- chanx 初始化参数（In/Out 容量 1024）取其常用默认；容量变化不改变
  交接次数，量级结论稳健。
- 未纳入对比：`x/sync/queue`（yqueue）——**经工具链验证，x/sync
  v0.23.0（截至 2026-09 最新发布版）不含该包**，此前情报有误，
  roadmap 已修正。官方动向持续跟踪。

## 对 v0.2 设计的输入

| 输入 | 来源 |
|---|---|
| MPSC 无锁化优先级最高，目标 ≤80 ns | 场景 C |
| SPSC 快路径已接近原生，不值得先动 | 场景 A |
| 交接次数是成本主项，无锁设计必须保持"1 次交接" | chanx 分析 |
| 排空 Close 语义是 yqueue 类实现普遍缺失的差异化 | 竞品调查 |
